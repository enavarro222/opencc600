# GEOID CC700: hardware survey and porting notes

All findings below were made on one CC700 unit on 2026-10-22, over the USB-C port only (case closed), with the vendor
firmware running. Every step was read-only: no flash write, no eFuse write. The method is the one used for the
CC600 in [REVERSE_NOTES.md](REVERSE_NOTES.md).

Paths starting with `dump/cc700/` refer to local files that are **not** in this repository.

## Summary

**The CC700 is the CC600 board.** Same SoC, same PSRAM, same partition table, same live pinout, same LCD_CAM
configuration, same ST7789 init sequence, same UART speeds. The vendor firmware is the same code base
(`CC600` / `MageneC606` / maps / IMU code are in both images). Our firmware should run on it with no driver change.

What differs, and what must change before we flash it:

| | CC600 | CC700 | Impact on our firmware |
|---|---|---|---|
| Vendor slot (update history, not the model) | **ota_1** (`506_SE_V1.407`), after one OTA update: ota_0 keeps the older `Venus_V1.313` | **ota_0** (`CC700_V1.414`), never updated: ota_1 empty | vendor image copied to ota_1 first: see *Moving the vendor firmware to ota_1* |
| Flash chip | Puya (0x85, 0x2018) | GigaDevice (0xC8, 0x4018), 16 MB | none (both quad 3.3 V, 16 MB) |
| External storage | none | **none**: no SDMMC pins configured, no FAT / SDMMC driver in the image (only a stray `hello emmc!`, also in the CC600 image); all data in the 7.8 MB littlefs | none |
| Screen (retail listings) | 2.4", 240x320, ~167 ppi | **2.8"**, 240x320, ~143 ppi | none in code (same controller init, same pixels); everything shows ~17 % larger |
| SPU ID (product id in the vendor log) | 345 | **389** | none; the board can be told apart at runtime only through the nRF (see below) |
| Internal product name (`ProductInfo.config`) | — | `C506SE`, BLE name `GEOIDCC700` | none |
| Vendor app version (`MasVersion`) | 1.408 | 1.415 | none |
| nRF firmware (`SlaVersion`) | 1.602 | **1.708** | to check: frames, rates, buzzer, sensor stream |
| `SpuVersion` | e08 | e0f | unknown meaning |
| 2nd stage bootloader | IDF `17977806-dirty` | same IDF tag, different build | none (we never write it) |

## Chip and memory

- USB: `303a:1001` Espressif USB JTAG/serial debug unit, `/dev/ttyACM0`, MAC / serial `7c:4f:ad:84:ae:a8`
- SoC: ESP32-S3 (QFN56) rev v0.2, dual core 240 MHz, Wi-Fi + BLE 5, 40 MHz crystal
- PSRAM: 2 MB embedded, quad (AP_3v3), 105 °C grade
- Flash: 16 MB quad, 3.3 V, **GigaDevice** (manufacturer 0xC8, device 0x4018). Boot log: SPI mode DIO, 80 MHz.
- Full dump: `esptool -p /dev/ttyACM0 -b 921600 read-flash 0 ALL dump/cc700/flash_full_16MB_cc700_20261022.bin`
  (88 s). It is the only way back to a stock CC700: keep it.

## Security (eFuses): everything is open

Same as the CC600 (`dump/cc700/efuse_summary.txt`): flash encryption off, secure boot off, all key purposes `USER`,
download mode and USB-Serial/JTAG download enabled, USB JTAG and pad JTAG enabled, `SOFT_DIS_JTAG` 0.
esptool reaches the ROM loader while the vendor firmware runs, and OpenOCD attaches over the same cable.

## Flash layout

The partition table at 0x8000 is **byte for byte the CC600 one**:

| Name | Offset | Size | CC700 content |
|---|---|---|---|
| nvs | 0x009000 | 16K | |
| otadata | 0x00d000 | 8K | entry 0 seq 1, entry 1 blank → **ota_0 active** |
| phy_init | 0x00f000 | 4K | |
| coredump | 0x010000 | 64K | empty |
| ota_0 | 0x020000 | 4224K | `CC700_V1.414-dirty`, Apr 24 2026 14:02:18, IDF `17977806-dirty`, project `Project` |
| ota_1 | 0x440000 | 4224K | **empty** |
| storage | 0x860000 | 7800K | littlefs, 35 / 1950 blocks used |

The vendor never ran an OTA update on this unit: the factory image sits in ota_0 and ota_1 was never written.

## Live pinout (JTAG)

`tools/reverse/read_pins.py` run from the `espressif/idf:v5.4.2` container (it carries OpenOCD and
`gpio_sig_map.h`; none is installed on the host):

```sh
docker run --rm --privileged -v /dev/bus/usb:/dev/bus/usb -v "$PWD:/w" -w /w espressif/idf:v5.4.2 bash -lc \
  'python3 tools/reverse/read_pins.py /opt/esp/tools/openocd-esp32/v0.12.0-esp32-20250422/openocd-esp32 \
   /opt/esp/idf/components/soc/esp32s3/include/soc/gpio_sig_map.h --raw dump/cc700/pins_raw.txt'
```

Raw output: `dump/cc700/pins_live.txt`. The routing table, the UART dividers and the 16 LCD_CAM registers are
**identical** to [pins_live.txt](pins_live.txt) (CC600):

- LCD i80 16-bit, D0..D15 = 4,38,5,37,6,36,7,35,8,34,9,33,10,47,11,48; CS 2, PCLK 3, DC 40, GPIO39 driven high (RD)
- Backlight GPIO45 (LEDC)
- nRF on UART2: TX 42 / RX 41, 115200 baud
- GNSS on UART0: TX 1 / RX 0, ~921600 baud
- GPIO 12, 13-18, 21 not configured: **no touch, no eMMC**, as on the CC600

Gotcha: right after an esptool command the chip stays in the ROM loader and every pad reads as reset state. Boot the
vendor firmware first (`tools/serial_log.py 12 --reset`, with the esptool Python because `pyserial` is not in the
system Python: `~/.local/share/uv/tools/esptool/bin/python`), then attach.

## Vendor firmware

- `ota_0` image: same code base as the CC600 `506_SE_V1.407`. 27 784 strings against 27 803, about 3 300
  differences on each side, almost all compressed data. The CC700 image still holds `MageneC606`, the maps
  (`/littlefs/NAVIGATION`, OpenStreetMap, `maproute_plan`), the IMU code (`ImuHandleAccData`, `MagnetometerProcess`,
  `/littlefs/ImuDisable.txt`) and the touch panel factory test, like the CC600 image. String presence therefore says
  nothing about the hardware.
- CC700-only strings worth noting: `CC700_V1.414-dirty`, the `2025 Geoid ... all rights reserved` copyright lines,
  `/littlefs/ModuleDataTest/ModuleDataTest.cfg`, `AppModuleTestManage`, `ImuEventFuncCbReg`, `FitDecodeFile`,
  `GetDeviceTypeByAdvServiceData`.
- **ST7789 init**: the vendor table (porch `0C 0C 00 33 33`, `A4 A1`, both gamma curves) is the same bytes as in the
  CC600 image and as `firmware/src/panel.rs`. Same panel, same resolution as far as the firmware is concerned.
- Boot log over USB-Serial/JTAG (`dump/cc700/boot_reset.log`): 2nd stage bootloader, partition table, app loaded
  from 0x20000. The app itself is silent, as on the CC600.

## Vendor storage (littlefs)

Mounts with `littlefs-python` (block 4096, 1950 blocks). Extracted to `dump/cc700/vendor_files/`. Nearly a factory
state: 14 files, no ride, no `/APP` (no pending nRF update), no A-GNSS file.

- `CONFIG/ProductInfo.config` (368 bytes, same layout as the CC600): model `C506SE` at 0x11, name `GEOIDCC700` at
  0x31, BLE MAC at 0x160, region `china` at 0x13E. The CC600 copy holds the paired phone name instead at the same
  offsets.
- `LOG/20230911.log`: one session, the first power-on. The nRF RTC had never been set (2023-09-10 20:13:51).
  Lines of interest:

  | Log line | CC700 | CC600 |
  |---|---|---|
  | `load SPU ID =…,SPU ManuID=…` | 389, 136 | 345, 136 |
  | `SpuVersion` | e0f | e08 |
  | `MasVersion` (ESP32 app) | 1.415 | 1.408 |
  | `SlaVersion` (nRF app) | 1.708 | 1.602 |
  | `Arm init` | V1.000_20230110_1636 | same |
  | Brand | `BRAND_OVERSEA_GEOID` | same |

  The SPU ID matches the FCC filings: 345 is the CC600 (2A2L5-345), so 389 is likely the CC700 (the CC700 Pro is
  2A2L5-390).
- Same power-on sequence as on the CC600: `SendQuerySlaveModeCmd`, then `SendPowerOnCmd` until the nRF answers,
  power-on reason 4 → `SYS_EVENT_POWER_ON_MANUAL`. The GNSS answers `$PAIR490` / `$PAIR491,1,0` (no EPO).
- Keys seen in the log: indexes 1 and 2, value 1 (click). Same encoding as the CC600.

## Moving the vendor firmware to ota_1 (2026-10-22)

This CC700 never got a vendor OTA update, so it runs the vendor firmware from ota_0, with ota_1 empty (the CC600 got
one, which moved its vendor firmware to ota_1; any device can be in either state). The flash tool then
only wrote ota_0, so the vendor image was first copied to ota_1 by hand. `tools/flash.py` now finds the vendor slot
itself and writes ours into the other one: this step is no longer needed.

otadata (entry = seq u32, label, state u32 at +24, CRC32 at +28; state 2 = `VALID`, 0xFFFFFFFF = `UNDEFINED`,
booted as valid):

| | entry 0 (0xd000) | entry 1 (0xe000) | boots |
|---|---|---|---|
| CC700, factory | seq 1, state 2, CRC 0x4743989a | blank | ota_0 |
| CC600, vendor | seq 1, state 2, CRC 0x4743989a (same bytes) | seq 2, state 0xFFFFFFFF, CRC 0x55f63774 | ota_1 |

The bootloader boots the slot `(seq - 1) % 2` of the valid entry with the highest seq, and ota_0 when otadata is
blank. ESP-IDF apps run from either OTA slot (the MMU maps the slot to the same virtual addresses).

Done: `dump/cc700/ota_0.bin` written at 0x440000 (hash verified), then the CC600 vendor otadata at 0xd000. The
bootloader logs `Loaded app from partition at offset 0x440000`, no reboot over 20 s, and the vendor app leaves
otadata unchanged (no rollback marking).

Backups (`tools/flash.py` keeps one directory per device, named after the eFuse MAC):

| File | Content |
|---|---|
| `dump/7c4fad84aea8/otadata.orig.bin` | the otadata that boots the vendor from ota_1 (`--restore-vendor`) |
| `dump/7c4fad84aea8/storage.orig.bin` | vendor littlefs as read just before the erase (`--restore-vendor --storage`) |
| `dump/7c4fad84aea8/storage.20261022-dump.bin` | vendor littlefs from the first full dump, before the vendor ran from ota_1 |
| `dump/cc700/otadata.factory.bin` | factory otadata (boots ota_0) |
| `dump/cc700/flash_full_16MB_cc700_20261022.bin` | full factory flash: the only way back to a stock CC700 |

The first erase was refused: the backup taken from the full dump no longer matched the device, because the vendor
firmware had written its log since. `tools/flash.py` now reads the partition again whenever its superblocks differ
from the backup, before it erases anything.

## First run of our firmware (2026-10-22)

Same build as the CC600 (no board option), flashed into ota_0. Boots from ota_0, PSRAM
2 MB, panel initialised, backlight on, GNSS output setup acknowledged (`PAIR062 -> 0` x7), 13 satellites in view
indoors, BLE up. nRF link both ways: buzzer `E2 01 XX` sounds (heard), key clicks received (`nrf Key { key: 2,
action: Click }`), the keys drive the UI. Storage: after `tools/flash.py --erase-storage`, our firmware formats the blank
partition at boot (`storage: blank partition, formatted`, 1948 / 1950 blocks free).

nRF details (debug build, `ESP_LOG="info,opencc600=debug"`, 2026-10-22):

- Version frame **1.8.17** (CC600: 1.2.16); `Ack` and power-on reason 4 as on the CC600. Battery and `F0` status
  as on the CC600 (4121 mV, 86 %, status 0 on USB).
- Same behaviour as the CC600 for the stream: absent after our flash (charging screen on USB), present after a
  long press of key 0, and it survived the ESP32 reset that followed.
- Barometer `F1 03` at 5 Hz, 1005.35 hPa, 31.9 °C (inside the case), noise **0.67 Pa** standard deviation at rest
  (CC600: 0.8 Pa).
- Light `F1 04` at 2.5 Hz, but the measurement tags differ: **30, 50 and 600** (CC600: 600, 2000, 3000), level
  ~264 at tag 50. Another sensor or another cycle: to map against covered / lit, as on the CC600.
- `F1 0A` present (u16 ~3780..3800 against ~3000..3100 on the CC600, still unknown).
- **No accelerometer / gyro frames** (`F1 01` / `F1 02`) over 13 s of stream: no IMU on the CC700 either.
- A long press of key 0 on our home screen powers off as on the CC600 (`SendPowerOffCmd`, the USB port disappears).

## Still to check on the device (needs our firmware running)

- nRF 1.708 against 1.602: version frame, power-on handshake, RTC set, key codes for all three keys, power off.
- Sensor stream after a long press of key 0: barometer `F1 03` and light `F1 04` rates, and whether the CC700 sends
  accelerometer / gyro / magnetometer frames (`F1 01` / `F1 02` / `F1 00`, absent on the CC600). The vendor image
  has the IMU code in both cases, so only the frames will tell.
- Buzzer `E2 01 XX` table: same sounds?
- GNSS: receiver version (`$PAIR020`), same output setup.
- Screen: measure the diagonal (listings say 2.8" against 2.4") and check our 240x320 test pattern fills it with no
  offset; compare colours side by side, since a different glass module could want other gamma values even though the
  vendor sends the same ones.
- Battery reading against the CC600 (different capacity would only change the percentage curve, if the nRF does
  not already report a percentage).
