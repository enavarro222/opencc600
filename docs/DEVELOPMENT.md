# opencc600: code, build and tools

How the code is organised, how to build and flash it, and the tools around it. The test strategy (PC, device,
field) is in [DEV_PROCESS.md](DEV_PROCESS.md), the hardware in [REVERSE_NOTES.md](REVERSE_NOTES.md).

## Code layout

[firmware/](../firmware/) is a standalone Cargo project for the Xtensa target (`esp` toolchain from `espup`). Its
`src/` is the board layer (panel, storage, BLE, ANT+, GNSS UART); `src/bin/opencc600/` the application that wires
the crates below to it: `main.rs` (boot and main loop), the tasks (`nrf.rs`, `receiver.rs`, `usb.rs` for the test
hook) and one module per concern (`ride.rs`, `trip_log.rs`, `route_file.rs`, `pairing.rs`, `config.rs`, `app.rs`
for the companion app, `screen.rs`).
The hardware-independent `no_std` crates live in the host workspace at the root, on the stable toolchain, and are
tested on a PC with `cargo test`:

- [crates/nrf-link/](../crates/nrf-link/): UART protocol with the nRF co-processor (frames, CRC, keys, battery, RTC,
  barometer, light, buzzer, commands).
- [crates/gnss/](../crates/gnss/): NMEA reader (checksums, error counters) and fix parser for the Airoha AG3352Q,
  `$PAIR` commands; tested on an anonymised capture.
- [crates/ride-store/](../crates/ride-store/): ride files on littlefs that survive a power cut; its test cuts the
  power at every flash operation of a recording scenario (RAM fake NOR flash).
- [crates/fit/](../crates/fit/): FIT activity writer; every file of its tests is decoded again with `fitparser`.
- [crates/recorder/](../crates/recorder/): ride recording as FIT on ride-store, pauses, totals, closing of
  interrupted rides; its test cuts the power at every flash operation of a ride and of the recovery.
- [crates/altitude/](../crates/altitude/): barometric altitude whose bias is calibrated on the GNSS (Kalman filter),
  tested on synthetic rides; see [ALTITUDE.md](ALTITUDE.md).
- [crates/sensors/](../crates/sensors/): BLE GATT measurements and ANT+ pages of the cycling sensors decoded, the
  ANT+ channels kept open, rates from cumulative revolution counts, the power meter's calibration.
- [crates/identity/](../crates/identity/): which device this is (CC600 or CC700, from the vendor's factory data in the
  `nvs` partition) and its Bluetooth name and address, from the MAC address (`OpenCC700 AEA8`).
- [crates/companion/](../crates/companion/): the BLE link with Musette (settings, routes, rides listed, read and
  acknowledged), in the frames of `protocol-cc600`.
- [crates/status/](../crates/status/): the device's state from the nRF and the GNSS receiver (battery, RTC,
  barometer, fix), and the time now: the GNSS one with a valid fix, else the RTC; a fix without an epoch for 3 s
  expires.
- [crates/test-hook/](../crates/test-hook/): the commands typed on the USB serial port by the HIL tests and the
  tools (keys, settings, routes, simulated position and light).
- [crates/ui/](../crates/ui/): screens, what the 3 keys do on each, drawing on the 240x320 panel
  (embedded-graphics) with the prototype's font, Barlow Condensed, anti-aliased (4-bit alpha, generated by
  `tools/build_fonts.py`); its test draws every screen to `target/tmp/screens/*.png` and stops on a missing glyph
  or a text out of the screen.

### Host-only crate

`route-tool` ([crates/route-tool/](../crates/route-tool/)) is the only host workspace crate that is not a direct
dependency of the firmware. It is a PC command-line tool, not part of the firmware image. Its
`build` command converts a GPX into the route file sent to the device, `map` builds a background map for a route,
and `sim` replays a GPX through the UI and writes screenshots. The simulator tests also call it to create route
and map files. Its coverage therefore belongs to host tooling; it does not measure firmware code coverage.

The file formats and the protocol shared with the app live in the MIT
[musette](https://github.com/enavarro222/musette) repository and come by git at a pinned `rev` (`Cargo.toml`):
`protocol-cc600` (BLE protocol, resumable file transfer), `route-cc600` (route `OCRT` with its climbs, corridor
map `OCMP`), `settings-cc600` (the settings file, POSIX time zones). To work on them, a `[patch]` towards a local
clone in an untracked `.cargo/config.toml`; bump the `rev` once the musette commit is pushed. Make targets omit
Cargo's `--locked` flag while a local Cargo config exists, so Cargo can resolve that patch. This can rewrite lockfiles
with local paths; do not commit those lockfile changes. Release preparation requires disabling local `[patch]` entries
so the committed locks keep the pinned Git sources used by CI.

## Build and flash

The root [Makefile](../Makefile) provides the common local and CI entry points. It expects the ESP Xtensa toolchain
from `espup` in `~/export-esp.sh`; the demo and release targets also need `espflash`, Python, and the pinned
esp32sim build or its release assets.

```sh
make help
make firmware                         # firmware ELF
make firmware-image                   # OTA-slot image at target/opencc600-ota.bin
make flash CC600_PORT=/dev/serial/by-id/... # check, build, confirm, and flash a selected device
make flash CC600_PORT=/dev/serial/by-id/... FLASH_AUTO_CONFIRM=1 # same preflight, no prompt (scripts)
make demo                             # browser build named main
make preview                          # stage the existing demo build and serve localhost:8765
make release NAME=v0.0.4              # build browser demo and release files under target/release/
make prepare-release VERSION=0.0.4    # update Cargo versions and lockfiles before a release
make test                             # host Rust tests
make coverage                         # host tests + HTML coverage report
make test-sim                         # firmware on the native CC600 emulator
make test-hil CC600_PORT=/dev/serial/by-id/... # connected device
make check                            # host and emulator tests, no device
```

Install `cargo-llvm-cov` once with `cargo install cargo-llvm-cov --locked`, then run `make coverage`; its HTML
report is written to `target/llvm-cov/html/index.html`. GitHub Actions runs the same coverage command on pull
requests and pushes to `main` and attaches the HTML report to the workflow run. The simulator job builds the
firmware and checks its emulator/ROM prerequisites before running pytest, so missing simulator dependencies
cannot make the job pass by skipping all tests. Physical-device tests (`make test-hil`) remain local.

`make preview` does not rebuild the firmware demo. Build it first with `make demo` (or `make site` for a full site build); while the preview server is running, page edits can be staged with `make site-copy` without restarting the server.

Generated demo files stay ignored by Git. The Pages workflow uses the same `demo`, `release` and `site-copy` targets; it runs on a tag or when manually dispatched.

### Preparing a release

The Cargo version is kept at the latest release version: one value in the root workspace is shared by its crates,
and the firmware has the same value in its separate manifest. Run `make prepare-release VERSION=0.0.4` with no
modified tracked files to update both manifests and their lockfiles. Untracked local files are allowed, but disable
local Cargo `[patch]` entries first so the lockfiles retain CI's pinned Git dependencies. It then runs `make check` to
validate host tests, the native simulator and firmware build. Review and commit those four
files, then tag and push the commit as `v0.0.4`. The Make target prints the commands; it does not commit, tag or
publish. The Git tag remains the
source for the version shown by the firmware (`v0.0.4`, or `v0.0.4+N` on later commits). The tag workflow checks
that both Cargo manifests and the locked package metadata match before building; a mismatch fails the CI. Pushing the
tag triggers the GitHub Pages build and GitHub release. `make release NAME=v0.0.4` only builds local demo and release
assets; it does not prepare versions or publish them.

For unattended flashing, pass `FLASH_AUTO_CONFIRM=1` to `make flash`. This skips only the interactive yes/no prompt;
port, ESP32-S3, partition-layout and vendor-fallback checks still run before the firmware is built. The default is
to ask for confirmation.

```sh
cargo install espup espflash --locked && espup install --targets esp32s3 && uv tool install esptool
. ~/export-esp.sh
cd firmware && cargo build --release
espflash save-image --chip esp32s3 --flash-size 16mb target/xtensa-esp32s3-none-elf/release/opencc600 ../dump/opencc600.bin
../tools/flash.py ../dump/opencc600.bin           # the slot the vendor does not use; --restore-vendor boots it again
../tools/serial_log.py 30                         # logs over the USB serial, host-timestamped
```

Host tests: `littlefs2` generates its C bindings with bindgen, which needs the clang C headers on the PC
(`sudo apt install libclang-common-18-dev` on Ubuntu 24.04, or the esp toolchain's clang:
`BINDGEN_EXTRA_CLANG_ARGS="--target=x86_64-unknown-linux-gnu -isystem $LIBCLANG_PATH/clang/21/include"`, with
`LIBCLANG_PATH` from `~/export-esp.sh`; never set while building the firmware).

Hardware-in-the-loop tests on a device plugged in over USB (keys injected over USB, storage read back):
`uv run --project tests/hil pytest tests/hil`, see [tests/hil/](../tests/hil/) and [DEV_PROCESS.md](DEV_PROCESS.md).

## Tools

Day to day:
- `tools/flash.py`: writes an app image to the OTA slot the vendor firmware does not boot, then an `otadata` that
  boots it, after checking the device has the known CC600 / CC700 partition layout; `--status` shows what each slot
  holds and which one boots; keeps each device's backups in `dump/<mac>/` (eFuse MAC); saves the original
  otadata once (`dump/<mac>/otadata.orig.bin`), `--restore-vendor` writes it back (`--storage
  dump/<mac>/storage.orig.bin` also puts the vendor storage partition back). When the storage partition holds the
  vendor's littlefs (v2.1; ours is v2.0), it backs it up to `dump/<mac>/storage.orig.bin` (an older backup is kept
  beside it) and erases it, for our firmware to format at its next boot (`--keep-storage` leaves it). Refuses any
  other offset.
- `tools/serial_log.py`: prints the USB serial log for N seconds, each line with the host time (no reset);
  `--send T:TEXT` types a test command at T seconds (`key 2 click`, `sound off`, `gnss cold`, `gnss time on`,
  `rtc shift -300`, `screen ?`, `set tz UTC0`, `get sound`, `settings ?`, `bench map`, `fix LAT_E7 LON_E7
  [MM_S [CDEG]]`, `fix off`, `light RAW` in place of the ambient light sensor, `light off`, `light ?` for the theme,
  the backlight and the sensor's raw levels).
- `tools/light_survey.py`: the ambient light sensor's raw levels in scenes set by hand (dark, a lamp, a headlamp),
  with the backlight at 10 % and 100 % (does the sensor see the screen?), on one or more devices at once.
- `crates/route-tool`: `cargo run -p route-tool -- build IN.gpx OUT [TOL_M]` makes a route file, `info FILE`
  describes one, `sim IN.gpx OUT_DIR [EVERY_S]` rides a GPX through the real UI and writes the screens as PNG.
- `tools/check_fit.py`: decodes FIT files with the official Garmin FIT SDK.

Tests on the device (Musette does the same over BLE for riders; these go over USB, for the HIL tests and
debugging):
- `tools/send_route.py FILE.gpx -p PORT`: sends a route over USB (`route begin/data/end`, every line with its
  CRC-16, resent until acknowledged); the device keeps it in `/route`.
- `tools/pull_rides.py`: copies the rides and the trip logs (`/logs/*.csv`) to `dump/rides/` and checks the rides
  with the Garmin FIT SDK (reads the flash: the device resets).
- `tools/replay_gpx.py FILE.gpx -p PORT [--speedup N] [--kmh V] [--from-km D]`: rides a GPX without going out, one
  position a second sent with `fix` in place of the receiver's (it takes over again 5 s after the last one).
- `tools/fake_sensor.py`: a fake BLE heart rate, speed / cadence and power sensor on the PC (BlueZ).
- `tools/ttff.py`: measures the GNSS time to first fix after forced restarts (full cold, cold with the RTC time,
  hot...), to run by a window; results in `dump/ttff.csv`.
- `tools/hil_storage.py`: resets the device at random moments while the `hil-storage` firmware records, checks that
  no acknowledged ride data is lost.

UI and prototype:
- `tools/build_prototype.py`: rebuilds the standalone UI prototype page
  ([prototype/index.html](prototype/index.html), from [prototype/prototype.dc.html](prototype/prototype.dc.html)).
- `tools/prototype_shots.py`: screenshots of the prototype's states and their text layout (`target/proto/`), the
  reference for `crates/ui`; `tools/compare_screens.py` puts them next to the firmware's screens.
- `tools/check_prototype_layout.py`: checks in headless Chromium that nothing on the prototype screen changes size
  between states.
- `tools/build_fonts.py`: rasterizes Barlow Condensed (`crates/ui/fonts/`) at the prototype's sizes, with the UI
  icons as glyphs, into `crates/ui/src/fonts/` (FreeType, HarfBuzz kerning and tabular figures).
- `tools/build_logo.py`: draws the splash screen's logo as SVG, stacked and wide, day and night, into
  `docs/logo*.svg`.
- The README's screenshots in [screens/](screens/) are copied from `target/tmp/screens/`.

Reverse engineering of the vendor firmware, in `tools/reverse/` ([REVERSE_NOTES.md](REVERSE_NOTES.md)):
- `read_pins.py`: reads the pin routing of a running ESP32-S3 over its built-in USB-JTAG (Espressif OpenOCD),
  read-only.
- `vendor_fit.py`: extracts the vendor's recorded rides from a storage partition image as standard FIT files.
- `vendor_dplus.py`: replays the vendor's ascent / descent algorithm (decompiled from the vendor app) on vendor FIT
  files and compares it with their session totals.
- `nrf_image.py`: extracts and decrypts the nRF's firmware from the vendor storage partition
  ([NRF_FIRMWARE.md](NRF_FIRMWARE.md)).
- `esp_image_elf.py`: turns an ESP32-S3 app image (an ota partition) into an ELF for Ghidra or objdump; `ghidra/`:
  headless scripts that name the mask ROM functions, decompile the functions using given strings or at given
  addresses (and their callees), and print the arguments of each call to a function.
